Start here

What nzbview is showing you

nzbview follows a release from the moment Sonarr or Radarr searches for it until SAB finishes the download and Arr imports it. It keeps those steps separate so a search problem is not mistaken for a provider problem, and a failed download is not mistaken for a failed import.

1. SearchSonarr/Radarr asks one or more indexers for releases.
2. GrabA release is selected and handed to SABnzbd.
3. DownloadSAB downloads, verifies, repairs and unpacks it.
4. ImportSonarr/Radarr moves the completed media into the library.

Two ways to look at the data

Time window
Shows everything inside a period such as the last day, 7 days or 14 days. Use this when you want to know what happened during a period of time.
Recent sample
Uses the newest fixed number of items, such as the last 50 or 100 grabs/downloads/searches, regardless of how long they took to happen. Use this when you want a fair performance sample.
Exact match
nzbview could directly connect the Arr/Prowlarr release name to the SAB job.
Episode fallback
The exact title did not match, but series + season + episode information was strong enough to connect the records safely.
Unresolved
nzbview saw part of the journey but does not have enough retained evidence to claim a final result.
{% elif help_topic == 'dashboard' %}
Dashboard

The quick health view

The Dashboard is the fastest place to see whether downloads and indexers are behaving normally in the selected window.

Attempt success
Of the SAB attempts that ended in success or failure, how many completed successfully.
Eventual success
How many unique releases eventually completed, even if an earlier attempt failed first.
Recovered
A release failed once, then a later attempt completed it.
Heavy repair
A release needed 10 or more PAR repair blocks. A high number can point to poor article availability or damaged uploads.
Live trends
Shows how outcomes, indexer success, search coverage and provider availability changed through the selected window. Hover the chart to see the exact values at a point in time. Click a legend item to hide or show that series.
Biggest changes
Compares the current window with the immediately previous window of the same length when enough data exists.
Attribution quality
Shows how confidently nzbview connected Arr/Prowlarr activity to the correct SAB release.
{% elif help_topic == 'activity' %}
Activity

The event timeline

Activity is the audit trail. It shows what happened at each stage instead of trying to collapse everything into one result.

Searches
Sonarr/Radarr search sessions seen in retained logs.
Hand-offs
Releases Sonarr/Radarr actually sent to SAB.
Downloads
SAB download results such as completed or failed.
Imports
Sonarr/Radarr import results after SAB finished. A SAB completion is not automatically treated as proof of import.
Pre-SAB
The release failed before SAB received it, for example an indexer/Prowlarr grab problem.
Infrastructure
Connection or availability problems between Arr and the download client.
History
Routine SAB/Arr history cleanup and archive actions.
Trigger
Whether the search appears automatic, an automatic retry after a previous failure, interactive/manual, RSS-related, or unclear from retained evidence.
{% elif help_topic == 'indexers' %}
Indexers

How well each indexer finds usable releases

Indexer Performance focuses on grabs and their download results. Raw Search Results focuses on what each indexer returned during searches before the download result is known.

Indexer Performance

Final success
Unique releases from the indexer whose final observed result completed.
Successful grabs
Grabs from that indexer whose own SAB attempt completed. If it failed and another indexer later recovered the media, the original grab still stays failed.
Attempt success
Successful downloads divided by successful + failed downloads for that indexer.
Repair needed / Heavy repair
How often releases needed PAR repair, with Heavy repair meaning 10 or more repair blocks.
Rescued from others
Another indexer failed first and this indexer later supplied the successful replacement.
Later rescued elsewhere
This indexer failed first and a different indexer later supplied the successful replacement.
Recent sample · Grabs
Each indexer gets its own newest N grabs. This lets you compare “last 100 grabs from altHUB” with “last 100 grabs from NZBgeek” instead of mixing them into one pool.

Raw Search Results

Availability
For searches where nzbview knows the wanted quality, the percentage where that indexer returned at least one matching release.
Queried searches
How many selected searches actually used that indexer. An indexer can have fewer than the total if Arr/Prowlarr did not query it every time.
Wanted-quality NZBs returned
The number of individual matching release candidates, not the number of searches. One search can return hundreds of NZBs, so this number can be much larger than the search count.
All NZBs returned
All retained candidates returned before later Arr filtering.
{% elif help_topic == 'providers' %}
Providers

What your Usenet servers actually supplied

Providers are not indexers. Indexers tell Arr where a release exists; providers are the Usenet servers SAB downloads the article data from.

Article availability
The percentage of requested Usenet articles that SAB could get from that provider.
Selected-window availability
Availability calculated from the change between stored provider snapshots around the selected time window.
Provider contribution
Approximate data volume supplied by each provider to retained downloads where SAB saved a server breakdown.
Downloads using multiple providers
SAB pulled data from more than one provider for the same job.
Downloads using one provider
Only one provider supplied data for the job.
Traffic share over time
How each provider's share of the observed download data changed through the selected window.
Recent sample
Uses only the newest downloads where SAB retained provider contribution data. It does not invent per-download article availability from cumulative counters.
ImportantA provider can have excellent article availability but a smaller traffic share simply because SAB used another equal-priority provider more often. Traffic share is not a win/loss score.
{% elif help_topic == 'downloads' %}
Downloads

What SAB actually tried to download

Downloads is organized by movie, episode or an observed whole-season Sonarr search. Expand a group to see the exact NZB releases SAB attempted.

Completed
That specific SAB attempt finished successfully.
Failed
That specific attempt failed. If a later attempt succeeds, the original attempt still stays failed and the later recovery is shown separately.
Season group
When retained Sonarr evidence shows a whole-season search, the related episode attempts are kept under one season parent. A single-episode search stays separate.
Repair blocks
How much PAR repair SAB reported for that attempt. More repair blocks generally means more missing/damaged article data had to be reconstructed.
Recent sample
The newest N completed/failed SAB download attempts, regardless of how much time they span.
Acquisition journeyClick an exact release name to open the full chain: Arr search → Prowlarr/indexer → SAB processing → final Arr import when retained evidence exists.
{% elif help_topic == 'releases' %}
Releases

One row per release acquisition

Releases groups repeated attempts of the same normalized release title into an acquisition chain so retries are easier to inspect.

Outcome
The final observed result for that release acquisition.
Retry chain
How many attempts were grouped into the same acquisition.
Repair
The largest repair-block count seen anywhere in that acquisition chain.
Recovered
An earlier attempt failed but a later attempt completed the same acquisition.
{% elif help_topic == 'recovered' %}
Recovered

Failures that later succeeded

This page answers “what failed first, and what eventually saved it?”

Cross-indexer
The failed attempt came from one indexer and the successful replacement came from another.
Same-indexer
The retry succeeded using the same indexer that supplied the earlier failed attempt.
Recovery path
The failed indexer → successful indexer pair, for example altHUB → NzbPlanet.
Repair
The highest repair-block count observed in the recovery chain.
{% elif help_topic == 'failures' %}
Failures

Downloads that are still failed

Recovered releases are intentionally excluded here. This page is for failures that still have no later successful replacement in the selected window.

Cause unavailable
SAB says the attempt failed, but the retained logs/API no longer contain a more specific reason.
Verification / Repair / Unpack
The most specific SAB stage associated with the final failure when that evidence was retained.
Repair severity
Groups failed releases by repair burden: no repair blocks, 1–9 blocks, or 10+ blocks.
Pre-SAB failure
The release failed before SAB received it. These are tracked separately from SAB download failures.
{% elif help_topic == 'diagnostics' %}
Diagnostics

Is nzbview seeing enough data to trust the other pages?

Diagnostics is mostly about collector coverage and evidence quality. You normally only need it when something looks wrong or a metric seems incomplete.

Attribution confidence
How reliably nzbview connected Arr/Prowlarr activity to the correct SAB job.
Rotating-log coverage
How many SAB, Prowlarr, Sonarr and Radarr log files/segments were found and read.
Rotation continuity
Checks whether the retained rotating logs still overlap the previous collector run. “Possible gap” means some older evidence may have rotated away before nzbview collected it.
Arr orchestration
Counts observed searches, hand-offs, retries, imports and connection problems in the selected window.
Evidence health
A compact summary of search-target reconstruction, release attribution, collector freshness and retained log coverage.
Live vs backfill
Live events are newer than the previous collector watermark. Backfill events are older records that were only discovered on the current run.
Collector freshness
How long ago the collector updated the database. Refreshing the browser does not collect new logs by itself.
Last collector run
Raw counters from the latest collection pass. These are useful for troubleshooting ingestion, not for judging indexer/provider performance.
